# 增量记忆整理与覆盖账本

增量整理从授权 Memory 中发现尚未分析的已登记来源版本，封存有界计划，再分批交给现有维护任务和独立 worker。
生成的候选继续走[人工审核与显式发布](memory-maintenance.md)，计划本身不会修改当前记忆。
它不提供定时触发、自动审核、自动发布或 Wiki。

## 选取范围与版本

只有 active 的受管 Memory 和已登记且 active 的 RAW 来源进入发现范围。
普通写入、来源登记及接管规则仍见[修订与来源](memory-revisions.md)；发现操作不会代替调用者接管旧数据。
来源数量与 `has_more` 描述这个登记范围，不能当成消息存储中的全部历史。

`scope` 的 `user_id`、`agent_id`、`session_id` 都是内容筛选器，不授予权限；每次请求重新检查当前 Memory 权限。
`null` 表示不限制该字段，空字符串表示精确匹配空值，不能将二者合并或自动修剪空白。
选取按稳定来源 ID 推进，不依赖会话创建时间或事件时间，因此旧会话续写及时间较早的新来源仍可被发现。

覆盖身份包含来源 ID、revision、generation、正文哈希和服务端分析配置指纹。
配置指纹包含范围、策略、输入／输出预算、分析提示版本、模型配置，以及显式目标记忆及其必要来源版本。
来源或分析配置变化后，需要重新判断覆盖；调整发现窗口或分批大小本身不表示已有分析失效。
旧手动任务没有这些证据，不自动回填为已覆盖。

## 预览、创建与提交

以下路径均在 `/api/v1/memories/{memory_id}` 下：

| 操作 | 路径 | 行为 |
| --- | --- | --- |
| 预览 | `POST /maintenance-discoveries/preview` | 只读选源元数据，不创建任务、不调用模型、不写覆盖账本 |
| 创建计划 | `POST /maintenance-discoveries` | 使用预览前置哈希封存计划和稳定子操作句柄，不调用模型 |
| 列出计划 | `GET /maintenance-discoveries` | 只读最近计划；可按原 `operation_id` 找回创建结果 |
| 读取计划 | `GET /maintenance-discoveries/{discovery_id}` | 聚合子任务、覆盖与延期状态，不推进执行 |
| 提交批次 | `POST /maintenance-discoveries/{discovery_id}/runs` | 每次显式提交有界数量的子任务，由现有 worker 执行 |
| 取消计划 | `POST /maintenance-discoveries/{discovery_id}/cancellations` | 取消未启动项，已创建任务沿原取消和排空协议处理 |

预览的选择请求示例：

```json
{
  "scope": {"user_id": "subject", "agent_id": null, "session_id": null},
  "policy": "general",
  "entry_ids": [],
  "batch_size": 16,
  "max_sources": 128,
  "input_budget_tokens": 16384,
  "output_budget_tokens": 4096
}
```

一次计划最多选择 256 个主要来源版本，每个子任务最多包含 32 个来源，每次提交最多推进 8 个子任务。
子任务按来源登记的 user/agent 作用域分组；同主体不同会话可以进入同批，不根据正文中的角色标签推断身份或事实已验证。
`entry_ids` 显式选入的旧记忆提供纠错上下文，其必要来源会重复带入对应主体的子任务，并占用批次容量。
上下文重复不会增加新发现来源数；没有剩余主要来源位置时明确拒绝，不形成空转批次。

创建请求使用相同选择字段，另带 `operation_id` 和预览返回的 `expected_preview_sha256`。
预览与创建之间来源、配置或选取结果变化时返回 409，应重新预览。
相同操作和请求重放返回原计划；不同请求不能复用同一个操作 ID。
提交请求使用自己的 `operation_id` 及 `limit`，取消也使用稳定操作 ID。
列表默认返回最近 20 条，`limit` 最多为 100；更早的已知计划可以按 ID 或原创建操作找回，不将该列表当作完整历史导出。

预览按已登记来源的版本元数据选源；显式旧记忆另检查其当前版本是否就绪。
`token_fit=not_checked` 不表示 RAW 正文能放入预算。
真正的正文选入由现有任务快照处理：整条超预算来源保留为延期，不截取开头后声称已分析整条。
同配置下已知预算阻塞的来源单独计数，不占满后续可处理来源的发现窗口；提高预算形成新分析配置后可以重新尝试。
输入与输出预算均按子任务使用，不是整个计划的总费用或总 token 承诺。

## 覆盖的含义

| 分类 | 含义 |
| --- | --- |
| `covered` | 对当前来源版本及配置完成了有效分析，且相关后台执行和实际写入占用已结算 |
| `inflight` | 当前版本已有尚未结算的处理句柄，不代表已分析 |
| `blocked` | 已知延期或预算阻塞，仍未覆盖 |
| `eligible` | 当前可选且尚未覆盖的来源版本 |
| `selected_primary` | 本次预览或计划选中的主要来源数 |

计划中的 `counts` 是创建时封存的选源统计，`progress` 按子批次数量描述执行进展，二者单位不同。
需要查看当前来源版本的有效覆盖时，应显式重新预览，不能把批次数直接除以来源数显示完成比例。

有效的空提议或 `noop` 可以确认来源已分析，避免没有新事实时无限重算。
未选入、延期、取消、坏响应、候选校验失败及结果未知都不能冒充完成覆盖。
候选和覆盖确认沿同一 SQL 决定保存；执行结算未知或实际调用尚未排空时，不向发现请求报告有效覆盖。
模型可能在失败恢复中再次调用并收费，账本不提供端到端 exactly-once 费用保证。

覆盖不表示事实正确、候选已批准、记忆已发布，也不表示所有来源之间的关系都已整合。
拒绝候选不会抹去已经完成的分析。需要重新分析时，可以显式创建普通维护任务，或在配置变化后创建新的增量计划。
模型质量与人工复核边界见[固定基线](memory-evaluation.md)。

## 恢复与生命周期

计划保存固定的子任务创建及分析操作 ID。请求断开或提交结果未知时，先读取原计划或按原创建操作查询，
不要换 ID 重发。只有原任务及其分析受理均已确认，批次才算已提交。
GET、Web 刷新和轮询不会自动提交、重试、对账或发布。

来源修订、停用、撤回、目标版本变化和 Memory 删除继续受原有来源及 writer 门禁约束。
旧版本的处理证据不能覆盖新版本，也不能凭租约过期认定实际调用已经结束。
计划与覆盖账本只保存版本、哈希、范围及操作元数据，不另存来源或候选正文副本。
整库删除后保留这些审计元数据，普通计划接口随 Memory 权限关闭；不把它们声明为已物理抹除。

部署前备份并应用新增 Alembic 迁移，再统一切换 API 和维护 worker；它们仍使用现有 worker 入口。
数据库与消息存储没有分布式原子事务；未知结果沿原句柄恢复，受管模式的备份及物理清除边界保持不变。
